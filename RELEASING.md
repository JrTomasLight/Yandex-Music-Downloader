# Как выпустить релиз

Релиз собирается автоматически (GitHub Actions, файл `.github/workflows/release.yml`):
стоит отправить на GitHub тег с версией, и через минуту на странице Releases появится релиз
с архивом `<ZIP_PREFIX>-<версия>.zip`, описанием из `CHANGELOG.md` и общим блоком
установки и обновления из `.github/release-template.md`.

## Шаги

1. Поменяйте версию в `extension/manifest.json`, например `"version": "1.2.0"`.
2. Добавьте описание версии в начало `CHANGELOG.md` под заголовком `## 1.2.0`, по шаблону из шапки
   `CHANGELOG.md`: подразделы «Новое», «Изменено», «Исправлено». Инструкцию по установке и обновлению
   писать не нужно — она добавляется в каждый релиз сама из `.github/release-template.md`.
3. Закоммитьте и отправьте изменения:

   ```bash
   git commit -am "Версия 1.2.0"
   git push
   ```

4. Создайте и отправьте тег с той же версией:

   ```bash
   git tag 1.2.0
   git push origin 1.2.0
   ```

Ход сборки виден на вкладке **Actions** репозитория.

## Пререлиз для проверки

Тег с суффиксом после версии — `0.1.0-beta.1`, `0.1.0-beta.2`… (в `manifest.json` остаётся `0.1.0`).
Такой релиз публикуется с пометкой Pre-release, архив называется `<ZIP_PREFIX>-0.1.0-beta.1.zip`,
а обновлением в один клик он не предлагается. Описание берётся из раздела `## 0.1.0` в `CHANGELOG.md`.

```bash
git tag 0.1.0-beta.1
git push origin 0.1.0-beta.1
```

## Если сборка упала

- **«Тег не совпадает с версией»** — тег и `version` в `manifest.json` разные.
  Тег `1.2` подходит к версии `1.2.0`, тег с буквой `v1.2.0` — тоже.
- **«В CHANGELOG.md нет раздела»** — нет заголовка `## <версия>`.

Чтобы отправить исправленный тег заново, удалите старый и создайте его ещё раз:

```bash
git tag -d 1.2.0
git push origin :refs/tags/1.2.0
git tag 1.2.0
git push origin 1.2.0
```
